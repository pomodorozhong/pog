# Project instructions

Route of Grace is a map-based Elden Ring route planner. See `docs/architecture.md` for how it works and why; status lives in GitHub milestones and issues.

## Handoff

`HANDOFF.md` at the repository root is how sessions resume. It has three sections: `In progress` (one `### <branch>` subsection per active branch, holding its state and its own approval requests), `Ranked work`, and `Pending` (approval requests not tied to a branch). A pending entry, such as `P-01`, records a request, not approval.

- **Start of a session:** read `HANDOFF.md` and the subsection named after `git branch --show-current`; no subsection means nothing is in progress on this branch. Compare its code checkpoint with `git log`, re-check verification that later commits may have made stale, and run the project's documented checks before building on it. If this branch's PR has merged or closed, apply the `commit` skill's branch-safety rules before new commits or pushes. To pick new work, start from the default branch's `Ranked work`.
- **Edit only this branch's subsection,** plus `Ranked work` and `Pending` when they actually change. Keep it current rather than a log, and never write secrets.
- **Commit `HANDOFF.md`** only before a push and at wrap-up, as a `docs:` commit on the work branch. Never commit it on the default branch.
- **PRs:** use the `open-pr` skill, and keep its unanswered approval requests in this branch's subsection until they are resolved. **End of a session:** use the `handoff` skill.
- **Before creating a branch, editing `HANDOFF.md`, or resolving a conflict in it,** read the `handoff` skill's working rules (`references/working-rules.md` in that skill).

## Working with the player

- Work is tracked in GitHub issues. Propose the top of `Ranked work` in `HANDOFF.md` to the player before starting. If it is labelled `needs-decision`, ask its questions first. The player can always name another issue or task instead; work without an issue gets one drafted.
- Comment freely on issues being worked on (handoff notes, decisions). Ask before filing a new issue.
- Lasting knowledge goes in `docs/` (index: `docs/README.md`), not in issues.

## Data

- Game data (item catalog, names, icons, map tiles) is generated by `npm run extract` (see `scripts/extract/README.md`). Never edit it by hand, and keep extracted assets (`game-data/`, `.cache/`) out of git.
- Official in-game names from the extracted data win over any other translation. Player-written text is kept as written.
- Player-authored data belongs to the player. Each playthrough profile has its own map (nodes and paths, `maps/<profile id>.json`), and player state (`player.json`: settings and the profiles, each with its own goal, constraints, wishlist and progress) is a separate file in the app data folder (`ROUTE_OF_GRACE_DATA_DIR` overrides it). Change them only when asked. The MCP tools (once they exist) cover the active profile's wishlist.
- Map coordinates are native map pixels of a layer (`overworld`, `underground`, `dlc`, `dlc-underground`). A path hop between two layers is a waygate jump.

## Interface

- All interface text supports English and Traditional Chinese (zh-TW). Write English in the code and add the zh-TW string to `data/localization/ui.zh-TW.json`.
- The mirror (`?mode=mirror`) is a read-only copy of the player's own app window (same open modals, scroll position, map view, laid out at its own size) for use as an OBS browser source, so the player never operates the app inside OBS. It is not an audience feature: there is one mirror, on the same computer. It accepts no input and never sends updates back, so state only flows from the app to the mirror.
- When adding a wishlist item, suggest its region and requirements, and ask the player to confirm the exact pin.

## Checks

`npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e` (needs `npm run extract` first; see `docs/testing.md`). Format with Prettier.

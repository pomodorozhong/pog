Milestone 3 (graces from game data) of [the plan](../plan.md) is done, and playthrough profiles, the first step of milestone 4, are built. This note keeps what the plan leaves out.

## Param layouts (from soulsmods/Paramdex `ER/Defs`)

| Param                   | Row size | Fields used (offset)                                                                                                        |
| ----------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------- |
| BonfireWarpParam        | 236      | `eventflagId` u32 @4, display mask u8 @30, `areaNo`/`gridXNo`/`gridZNo` u8 @32–34, `posX/Y/Z` f32 @36–44, `textId1` s32 @48 |
| WorldMapLegacyConvParam | 48       | source `area, gridX, gridZ` u8 @4–6 + `pos` 3×f32 @8; destination the same at @20 and @24                                   |

- **Display mask:** bit 0 = shown on the surface map, bit 1 = shown on the underground map. Every DLC grace has mask 0.
- **`textId1`:** a `PlaceName` text ID, so grace names come from the same tables as place names.

## Legacy conversion

- **Rows:** 196. A row says "this point in map A is that point in map B"; the difference is a pure translation, no rotation or scale.
- **Both ways:** some maps only appear as a destination (Elden Beast's arena, area 19, is reached through the row `11_05 → 19`), so rows are followed in both directions.
- **Chains:** Deeproot Depths (12_03) goes through the Leyndell sewers (35) and Leyndell (11) to the overworld. The search prefers a direct link to area 60/61, then the conversion point nearest the grace.
- **Unresolved:** 3 rows: the unnamed row 0 and two unnamed rows in area 12_06.

## Finding the transform

- **What didn't work:** scoring candidate transforms by how many graces land on "land" (red − blue on the map image). The optimum was broad and noisy, and a scale bug in the first script made every candidate look perfect.
- **What worked:** crops of the map around graces at drawn landmarks. With the old guess (7040, 16640), Church of Elleh, Church of Dragon Communion and Third Church of Marika were all about 110–130 px south of their drawings. Moving to 16512 put them on the drawings within about 20 px.
  - **Round numbers:** 7040 = 27.5 × 256 and 16512 = 64.5 × 256, half-cell values, which suggests these are the game's own constants.
- **DLC:** the land score for the DLC map peaked at scale 1.0 with an offset within 50 px of the overworld's. With the exact overworld transform, Church of the Bud, Cathedral of Manus Metyr, Fort of Reprimand, Scadutree Base, Belurat and Shadow Keep all sit on their drawings.
- **Underground:** the same transform puts all 30 underground graces (Siofra, Nokron, Ainsel, Lake of Rot, Deeproot) on the drawn caverns.
- **Legacy dungeons:** Stormveil, Raya Lucaria, Leyndell, the Elden Beast arena (projected onto the Erdtree) and Shadow Keep line up too.
- **Stone Coffin Fissure:** its four graces, including the open-world "The Fissure", land south of the Cerulean Coast over the sea. The open-world grace is there too, so this matches the game's own coordinates.

## Map gestures (2026-10-14)

- **Trackpad:** two-finger scroll pans, and pinch zooms around the fingers. macOS browsers report a pinch as a `wheel` event with `ctrlKey`; Safari's `gesture*` events are cancelled so the page itself doesn't zoom.
- **Mouse wheel:** still zooms around the cursor. It's told apart from a trackpad by line-based deltas or a legacy `wheelDeltaY` in multiples of 120 with no horizontal movement (`src/map/gestures.ts`).
- **Smoothness:** fractional zoom (`zoomSnap: 0`), and zoom eases toward its target every animation frame. The saved view is reported 150 ms after movement stops, not on every frame.
- **Touch screens:** keep Leaflet's own drag and pinch.
- **Testing:** browser test with synthetic wheel events (pan, pinch, wheel, default prevented, view saved with fractional zoom). Not tested on a real trackpad; how it feels may need tuning (`PINCH_SPEED`, `WHEEL_SPEED`, `EASING`).
- **Fix (2026-10-14): tiles blanked out during pinch.** `setZoomAround` resets the view on every frame, and Leaflet then discards all tiles (`viewprereset`). Zoom frames now go through the same private calls as Leaflet's touch pinch (`_move` with `pinch: true`), so existing tiles are scaled and kept until the new level loads. The gesture ends 120 ms after the last event with a `zoom` event (prunes old tiles) and `_moveEnd`. Measured over a synthetic pinch that crossed two zoom levels: before, the map had blank areas in 125 of 194 frames; after, in 0 of 193.

## Map per profile and import (2026-10-14)

- **Storage keys:** documents are `player` and `maps/<profile id>`, served at `/api/state/<key>`. Anything else is a 404, so a key can't leave the data folder.
- **Upgrade:** reading `profile-1`'s map moves an old `map.json` into `maps/profile-1.json` with link + unlink, so it never overwrites a map already there. Tested on a scratch copy of the player's data (5 nodes, 2 paths moved over).
- **Deleting a profile:** the server moves its map to `deleted/maps/<id>.json` when `player.json` is saved without that profile (a timestamp is added if the name is taken). The client needs no extra request.
- **Switching profiles:** the last unsaved map edit is saved at once, and the next map's load waits for that save (one storage client per document). Undo history is kept per profile for the session, and dropped if the map changed in another window meanwhile.
- **Import from another playthrough** (side panel, nothing selected): pick a profile and optionally a layer. One batch, one undo step. Nodes are reused when the target has the same node ID (an earlier import) or the same game grace, so importing again only brings what's new. A path is skipped if the same type is already drawn between the same two nodes. With a layer picked, waygates still come across when their other end is already on the map.
- **Testing:** browser test on the scratch data folder (new profile empty, import 5 + 2, re-import 0 + 0, undo history kept across switches, deleted profile's map moved). Unit tests are now 20.

## Wishlist per profile

Version 2 profiles are upgraded with an empty wishlist; version 1 files go straight to version 3.

## Progress per profile

- **Storage:** `player.json` schema version 4 adds `progress` to each profile: `flags` (sorted game event flags known to be set) and `position` (a node ID on the profile's map, or null). Versions 2 and 3 are upgraded by adding whatever the profile is missing. Templates start with empty progress.
- **Why flags:** the save import reads event flags, and graces, items and bosses are all flags in the game, so one list holds them all. Only graces have their flag in the extracted data so far (`BonfireWarpParam`); picked-up items and beaten bosses can be stored but not named until those flags are extracted.
- **UI:** a selected grace linked to a game grace has "Discovered in this playthrough"; any node has "I'm here". The side panel shows "{count} of {total} graces discovered" and the position, with a link to it and Clear. On the map, undiscovered game graces are unlit (grey, no glow) and the position node has a blue ring.
- **Testing:** browser test on the scratch data folder (version 3 file upgraded, 279 game graces added, one marked discovered and set as position, both saved). Unit tests are now 28.

## Import progress from save

- **Reading the save (`server/save.ts`):** the server reads `ER0000.sl2` into memory (never writes it), checks the MD5 of the summary and of the slot it reads, and walks the slot's sections to the event flags, following er-save-manager's documentation. A checksum mismatch (the game mid-save) returns 409 and asks the player to try again. The save folder defaults to the CrossOver "Elden Ring" bottle; `ROUTE_OF_GRACE_SAVE_DIR` overrides it.
- **Event-flag table:** a flag's position is `table[flag / 1000] × 125 + (flag % 1000) / 8`, bit `7 − flag % 8`. The block table (`eventflag_bst.txt`, 11,919 blocks) was reverse-engineered by the community and can't be derived from the game files. Every save tool vendors ER-Save-Lib's copy, which has no license. The server reads it from `game-data/eventflag_bst.txt`. **Decision (from the player):** `npm run extract` downloads it from ER-Save-Lib at a pinned commit and checks its SHA-256, so nothing unlicensed goes into the repo. Item and boss flags wait: items with milestone 6, bosses when routing needs them.
- **API:** `GET /api/save/slots` lists each Steam account's characters; `POST /api/save/flags` returns which of the given flags are set for one slot. Local requests only, like storage.
- **Profile link:** `player.json` schema version 5 adds `save` (`steamId`, `slot`, `name`, or null) to each profile.
- **UI (progress section):** "Import progress from save" asks which character the first time, then reuses the link. If the linked slot now holds a character with another name, it asks before importing. A review shows "+N graces discovered, −N not discovered" with the names, and nothing changes until Apply. The save decides every grace flag; other flags are kept.
- **Bug found while testing:** JavaScript's `&` gives a signed result, so `handle & 0xf0000000` never equalled `0x80000000` and weapon entries were read with the wrong length. Fixed with `>>> 0`, and the test save includes a weapon handle.
- **Testing:** on a scratch copy of the player's save: slot 1 "Burning" has 140 discovered graces (Roundtable Hold among them) and slot 2 "55688" has 2 (Stranded Graveyard, Church of Elleh). Browser test: pick character, review +139 (one was already marked by hand), apply, re-import shows no changes, renamed-slot prompt. Unit tests use a synthetic save and are now 32.
